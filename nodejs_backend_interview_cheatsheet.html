1. JavaScript essentials for backend

Node.js runs JavaScript outside the browser. Strong JavaScript fundamentals make backend behavior easier to understand.

Execution context and call stack

An execution context is the environment in which JavaScript code runs. It keeps track of variables, scope and the code being executed. The call stack tracks which function is currently running.

function first() { second(); }
function second() { console.log("Hello"); }
first();

// Stack: first() → second() → console.log()
// Functions return in reverse order.

Interview question: What happens when a function calls another function? The new function is pushed onto the stack. When it finishes, it is popped off.

var, let and const; hoisting

  • var is function-scoped and can be redeclared. Its declaration is hoisted and initialized with undefined.
  • let and const are block-scoped. They are hoisted but cannot be accessed before declaration because of the temporal dead zone.
  • const prevents reassignment, but an object or array stored in it can still be mutated.
console.log(a); // undefined
var a = 10;

// console.log(b); // ReferenceError
let b = 20;

const user = { name: "Sam" };
user.name = "Lee"; // allowed

Closures and lexical scope

A closure happens when a function remembers variables from the scope where it was created, even after that outer function has finished.

function makeCounter() {
  let count = 0;
  return function () {
    count += 1;
    return count;
  };
}
const counter = makeCounter();
counter(); // 1
counter(); // 2

Where useful? Private state, function factories, callbacks and middleware configuration.

Promises and async/await

A Promise represents a result that may be available later. It can be pending, fulfilled or rejected. async/await is syntax that makes promise-based code easier to read. It does not make a slow operation execute synchronously.

async function getUser(id) {
  try {
    const response = await fetchUser(id);
    return response;
  } catch (error) {
    throw new Error("Could not load user", { cause: error });
  }
}

Remember: use Promise.all() for independent tasks that can run together. It rejects if any input promise rejects. Use Promise.allSettled() when you need every outcome.

Event loop: microtasks and macrotasks

JavaScript runs synchronous code on the call stack. When the stack is clear, the event loop coordinates queued callbacks. Promise handlers and queueMicrotask() are microtasks. Timers such as setTimeout() run through event-loop phases.

console.log("A");
setTimeout(() => console.log("timer"), 0);
Promise.resolve().then(() => console.log("promise"));
console.log("B");

// A, B, promise, timer (typical ordering)

In Node.js, also learn process.nextTick() and setImmediate(). Their exact ordering can depend on context. Avoid endlessly scheduling microtasks because they can starve I/O.

this, call, apply and bind

For a regular function, this depends on how the function is called. Arrow functions do not create their own this; they capture it from the surrounding scope.

  • call(thisArg, a, b): invokes now with individual arguments.
  • apply(thisArg, [a, b]): invokes now with arguments in an array.
  • bind(thisArg): returns a new function with a bound this.

Prototypes and inheritance

JavaScript objects can inherit properties and methods from another object through the prototype chain. When a property is not found on an object, JavaScript checks its prototype.

const animal = { speak() { return "sound"; } };
const dog = Object.create(animal);
dog.speak(); // "sound"

Shallow copy vs deep copy

A shallow copy copies only the first level. Nested objects are still shared references. A deep copy also copies nested structures. structuredClone() supports many common data types, but not every possible value such as functions.

const original = { profile: { city: "Mangalore" } };
const shallow = { ...original };
shallow.profile.city = "Bengaluru";
console.log(original.profile.city); // Bengaluru

const deep = structuredClone(original);

Debounce vs throttle

Debounce waits until calls stop for a chosen period. Good for search input. Throttle limits how often a function can run. Good for scroll or resize handlers.

Memory and garbage collection

V8 automatically reclaims memory that is no longer reachable. A memory leak occurs when code unintentionally keeps references to objects it no longer needs. Common causes include unremoved event listeners, unbounded caches, long-lived timers and retained request data.

2. Node.js internals

This is a high-value interview area. Understand the moving parts and how a request is processed.

What is Node.js?

Node.js is a JavaScript runtime built on Google's V8 engine. It lets JavaScript run outside a browser, commonly for APIs, scripts and real-time services. Node.js is especially effective for I/O-heavy work such as database calls and network requests.

V8, libuv and the operating system

  • V8: Executes JavaScript and manages its memory.
  • libuv: Provides the event loop and cross-platform asynchronous I/O support. It also manages a worker pool for certain operations.
  • Operating system: Handles many network and file operations using its underlying facilities.
Simple mental model: Your JavaScript starts work, delegates suitable I/O to the runtime or operating system, and continues running. When the operation completes, its callback can be scheduled for JavaScript to process.

Is Node.js single-threaded?

JavaScript in a typical Node.js process runs on one main event-loop thread. That does not mean the whole runtime uses only one thread. The operating system handles asynchronous I/O, libuv has a worker pool for selected tasks, and you can create worker threads for CPU-heavy JavaScript.

Good use cases: APIs, real-time apps and I/O-heavy services. CPU-heavy work on the main thread can block every request sharing that event loop.

Event loop phases

Know the broad purpose of these phases:

  1. Timers: callbacks for expired setTimeout and setInterval timers.
  2. Pending callbacks: certain system-level callbacks deferred from a previous cycle.
  3. Poll: retrieves and processes I/O events and callbacks.
  4. Check: runs setImmediate() callbacks.
  5. Close callbacks: handles some close events, such as a socket closing.

Node also processes microtasks between callback execution opportunities. Do not claim that a timer runs at an exact guaranteed millisecond; its delay is a minimum threshold, not a precise schedule.

process.nextTick() vs setImmediate()

process.nextTick() schedules a callback to run after the current operation, before the event loop continues. setImmediate() schedules work for the check phase. Recursive nextTick() calls can starve I/O, so use them carefully.

Thread pool and worker threads

The libuv worker pool is used for certain tasks, including many filesystem operations, DNS lookup operations and cryptographic functions. It is not where every HTTP request is processed.

Worker Threads run JavaScript in separate threads and are useful for CPU-intensive calculations. For normal network I/O, asynchronous APIs are usually the better choice.

Cluster vs Worker Threads

ClusterWorker Threads
Multiple Node.js processes, each with its own event loop and memory.Multiple JavaScript threads inside one process.
Useful for using multiple CPU cores to serve requests.Useful for CPU-heavy work and parallel computation.
Processes do not share normal in-memory objects.Can communicate via messages and can share memory using supported mechanisms.

Streams, buffers and backpressure

A Buffer represents binary data. A Stream lets you process data piece by piece instead of loading the entire file into memory.

  • Readable: data can be read from it.
  • Writable: data can be written to it.
  • Duplex: readable and writable.
  • Transform: duplex stream that changes data as it passes through.

Backpressure happens when a producer sends data faster than a consumer can handle it. Streams help regulate flow. Use pipeline() to connect streams and handle errors and cleanup more safely.

const fs = require("node:fs");
const { pipeline } = require("node:stream");

pipeline(
  fs.createReadStream("large-input.csv"),
  fs.createWriteStream("copy.csv"),
  (error) => {
    if (error) console.error("Pipeline failed:", error);
    else console.log("Copy complete");
  }
);

Graceful shutdown

When a process receives a shutdown signal, stop accepting new requests, allow in-flight work to finish within a time limit, close database and message-queue connections, then exit. This avoids dropping requests during deployments.

process.on("SIGTERM", async () => {
  server.close(async () => {
    await database.close();
    process.exit(0);
  });

  setTimeout(() => process.exit(1), 10000).unref();
});

This is a simplified illustration. Production code should also handle repeated signals, errors and the timeout carefully.

3. Express.js and REST API engineering

Know how a request travels through your application and how to keep API code maintainable.

Express middleware

Middleware is a function that runs during the request-response cycle. It can inspect or modify the request, send a response, or call next() to pass control onward.

function requestLogger(req, res, next) {
  console.log(req.method, req.path);
  next();
}

app.use(requestLogger); // register before routes

Order matters. Authentication and validation middleware should run before protected route handlers. Error middleware has four parameters: (err, req, res, next).

Controller, service and repository layers

  • Route: maps URL and HTTP method to a handler.
  • Middleware: cross-cutting work such as authentication.
  • Controller: handles HTTP details and sends the response.
  • Service: contains business rules.
  • Repository/data layer: reads and writes data.

Separating these responsibilities makes code easier to test and change. Avoid creating layers that add no value to a small application.

Centralized error handling

Instead of writing response logic for every error, pass errors to one error handler. Return safe, consistent messages to clients and log useful details internally. Never expose stack traces or secrets in production responses.

app.use((err, req, res, next) => {
  const status = err.statusCode || 500;
  console.error(err); // use structured logging in production
  res.status(status).json({
    error: status === 500 ? "Internal server error" : err.message
  });
});

HTTP methods and status codes

MethodTypical use
GETRead a resource. Should not change server state.
POSTCreate a resource or trigger an operation.
PUTReplace a resource. Usually idempotent.
PATCHPartially update a resource.
DELETEDelete a resource. Intended to be idempotent.

Useful status codes: 200 OK, 201 Created, 204 No Content, 400 Bad Request, 401 Unauthenticated, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable Content, 429 Too Many Requests, 500 Internal Server Error, 503 Service Unavailable.

REST, idempotency and API design

REST uses resources and standard HTTP semantics. An operation is idempotent if repeating the same request has the same intended effect as doing it once. GET, PUT and DELETE are designed to be idempotent; POST is not automatically idempotent.

For operations such as payments, accept an idempotency key, store the result associated with that key, and return the same result for retries. Protect the key with a uniqueness constraint or equivalent atomic mechanism.

Pagination: offset vs cursor

// Offset pagination
GET /users?limit=20&offset=40

// Cursor pagination
GET /users?limit=20&after=eyJpZCI6MTIzfQ

Offset pagination is simple but large offsets can become slow and rows can shift between pages as data changes. Cursor pagination uses a stable sort key and is usually better for large, frequently changing datasets. Always use a deterministic order, such as creation time plus unique ID.

Validation, rate limiting and CORS

  • Validation: check types, required fields, formats, ranges and business rules at the API boundary. Libraries include Zod and Joi.
  • Rate limiting: restrict requests per user, IP or API key over a time window. A shared store such as Redis is useful across multiple app instances.
  • CORS: browser security policy controlling which origins can read cross-origin responses. It is not authentication. Preflight requests use OPTIONS to check whether the actual request is allowed.

Timeouts and external API calls

Set timeouts so a slow dependency does not hold resources forever. Retry only errors that may recover, use exponential backoff with jitter, and cap attempts. Do not blindly retry non-idempotent operations such as payments unless you have an idempotency strategy.

4. Databases: SQL, MongoDB and Redis

You should know how to model data, protect consistency and investigate slow queries.

SQL joins

  • INNER JOIN: only rows with matches in both tables.
  • LEFT JOIN: every row from the left table plus matching right-side data; unmatched right values are NULL.
  • RIGHT JOIN: every row from the right table plus matching left-side data.
SELECT users.name, orders.total
FROM users
LEFT JOIN orders ON orders.user_id = users.id;

Indexes

An index is an extra data structure that helps a database find rows without scanning the whole table. It speeds up suitable reads but uses storage and adds work to inserts, updates and deletes.

A composite index covers multiple columns. Column order matters: an index on (status, created_at) is generally useful for queries filtering by status, and often by both columns. Check the query plan rather than guessing.

ACID transactions

  • Atomicity: all operations succeed or the transaction is rolled back.
  • Consistency: constraints and rules remain valid.
  • Isolation: concurrent transactions do not interfere beyond the configured isolation guarantees.
  • Durability: committed data survives failures according to the database's guarantees.

Use transactions when multiple database changes must succeed or fail together, such as creating an order and reserving inventory.

Isolation levels and deadlocks

Isolation levels control what one transaction can observe from another. Common SQL levels include Read Uncommitted, Read Committed, Repeatable Read and Serializable. Exact behavior differs by database.

A deadlock occurs when transactions hold locks the others need, creating a cycle. Databases detect and abort one transaction. Reduce risk by accessing records in a consistent order, keeping transactions short and retrying safe aborted transactions.

Normalization and query optimization

Normalization organizes relational data to reduce duplication and update anomalies. Use joins to retrieve related data. To investigate slow SQL, inspect the execution plan with EXPLAIN or the database's analyze option, check scans and joins, and confirm indexes match real query patterns.

Connection pooling

Opening a new database connection for every request is expensive. A connection pool reuses a limited number of connections. Set pool limits sensibly: across many application instances, total possible connections can exceed the database's capacity.

MongoDB: documents and schema design

MongoDB stores BSON documents in collections. Embed related data when it is usually read and updated together and its size is bounded. Reference data when it is large, shared by many records or independently managed. Model around your common queries.

MongoDB aggregation pipeline

An aggregation pipeline passes documents through stages to filter, reshape, group and calculate results.

db.orders.aggregate([
  { $match: { status: "paid" } },
  { $group: {
      _id: "$customerId",
      totalSpent: { $sum: "$amount" }
  }},
  { $sort: { totalSpent: -1 } }
]);

Common stages: $match, $project, $group, $sort, $limit, $lookup and $unwind. Filter early where possible and inspect query performance.

MongoDB indexes, replica sets and sharding

Indexes speed up queries that match their keys. A replica set keeps multiple copies of data for availability and failover. Sharding distributes data across machines when a single deployment cannot handle the data volume or throughput. Shard-key choice is important because it affects distribution and query routing.

Redis and caching

Redis is an in-memory data store commonly used for caching, counters, sessions, queues and coordination. It is fast, but cache data can be stale or lost depending on configuration. Your database should generally remain the source of truth for durable business records.

Cache-aside: check cache first; on a miss, read the database and populate the cache. On writes, update the database and invalidate or refresh the cache. Set a TTL so old entries expire.

Cache stampede: many requests miss the same expired key and hit the database together. Mitigate with request coalescing, short randomized TTL variation, locks or stale-while-revalidate strategies.

5. Authentication and security

Authentication asks who you are. Authorization asks what you are allowed to do.

JWT authentication flow

  1. User submits credentials over HTTPS.
  2. Server verifies credentials.
  3. Server issues a signed access token, and often a refresh token.
  4. Client sends the access token with protected requests.
  5. Server verifies signature, expiry and relevant claims before allowing access.

A JWT is usually signed, not encrypted. Do not put passwords or sensitive personal information in its payload.

Access tokens and refresh tokens

Access tokens are short-lived credentials used to call APIs. Refresh tokens last longer and are used to obtain new access tokens. Store refresh tokens carefully, rotate them on use, detect reuse where possible, and provide a way to revoke sessions. Cookie-based storage needs appropriate Secure, HttpOnly and SameSite settings plus CSRF protection based on the design.

OAuth 2.0 and OpenID Connect

OAuth 2.0 is an authorization framework that lets an application obtain limited access to a resource. OpenID Connect adds an identity layer on top of OAuth 2.0 so the client can authenticate a user. For modern user sign-in, use Authorization Code Flow with PKCE where appropriate.

RBAC and password hashing

RBAC assigns permissions to roles, such as admin, manager and user. The application checks whether the authenticated user has the required permission for an action.

Never store plain-text passwords. Use a password-hashing algorithm designed for passwords, such as Argon2id or bcrypt, with appropriate parameters and unique salts. Hashing is one-way; encryption is reversible with a key.

Common web vulnerabilities

  • SQL injection: attacker changes a query through untrusted input. Use parameterized queries.
  • NoSQL injection: untrusted input changes query operators or structure. Validate input and avoid passing raw objects into database filters.
  • XSS: attacker-controlled script runs in a user's browser. Escape output, sanitize appropriate HTML and use a Content Security Policy.
  • CSRF: tricks a browser into sending an authenticated request. Use CSRF protections where cookie-based authentication requires them, plus SameSite cookies and origin checks.
  • Broken access control: users access records or actions they should not. Check permissions on the server for every protected operation.

HTTPS, encryption and secrets

HTTPS protects data in transit using TLS. Encryption at rest protects stored data. Keep API keys, database passwords and signing secrets out of source code. Use a secrets manager or protected deployment environment, rotate credentials and grant only the permissions required.

6. Microservices and distributed systems

A distributed system has multiple components communicating over a network. Networks fail, messages can be delayed and a request can succeed even when the caller never receives the response.

Monolith vs microservices

A monolith is one deployable application. It is often simpler to develop, test and operate early on. Microservices split a system into independently deployable services around business capabilities. They can improve independent scaling and ownership, but add network failures, deployment complexity, observability needs and data-consistency challenges. Do not choose microservices just because they sound advanced.

Synchronous vs asynchronous communication

Synchronous: service A calls service B and waits for a response, commonly over HTTP or gRPC. It is straightforward but couples availability and latency.

Asynchronous: service A publishes a message and continues. A consumer processes it later. This reduces direct coupling but introduces eventual consistency, retries and duplicate-delivery concerns.

Kafka vs RabbitMQ

KafkaRabbitMQ
Distributed event log with retained, ordered records per partition.Message broker with exchanges, queues and routing.
Useful for event streams, replay and high-throughput data pipelines.Useful for task queues and flexible message routing.
Consumers track offsets.Consumers acknowledge messages.

Both have more capabilities than this short comparison suggests. Choose based on delivery, routing, replay and operational needs.

Delivery guarantees and idempotent consumers

At-most-once can lose messages but avoids redelivery. At-least-once retries until acknowledged but can deliver duplicates. Exactly-once claims usually have a specific scope and require careful design.

Make consumers idempotent: processing the same message twice should not create duplicate business effects. Store a unique message or operation ID and enforce uniqueness transactionally.

Retries, exponential backoff and dead-letter queues

Retry temporary failures with increasing delays, add random jitter, and set a maximum attempt count. Do not retry permanent validation errors. After repeated failures, move the message to a dead-letter queue (DLQ) for inspection and controlled replay.

Circuit breaker

A circuit breaker stops calls to a dependency that is repeatedly failing. It commonly has three states: closed (calls flow), open (calls fail fast), and half-open (a few test calls are allowed). It prevents one unhealthy dependency from exhausting resources across your application.

Saga and eventual consistency

A saga coordinates a business transaction across multiple services as a sequence of local transactions. If a later step fails, compensating actions try to undo earlier business effects. Eventual consistency means replicas or services may temporarily disagree but are expected to converge.

7. Backend system design essentials

In an interview, clarify requirements first, draw the main components, describe data storage and APIs, then discuss failure cases and scaling.

A repeatable system design approach

  1. Clarify requirements: users, main features, traffic, latency and availability expectations.
  2. Define APIs: identify key operations and request/response shapes.
  3. Model data: entities, relationships, indexes and constraints.
  4. Draw components: client, load balancer, API service, database, cache, queue and workers.
  5. Trace a request: explain what happens from request to response.
  6. Handle failures: timeouts, retries, duplicates, partial failure and recovery.
  7. Scale: identify bottlenecks and scale only the parts that need it.

Load balancing and horizontal scaling

A load balancer distributes incoming requests across application instances. Vertical scaling adds resources to one machine. Horizontal scaling adds more machines or instances. For horizontal scaling, avoid relying on process-local sessions or caches unless they are intentionally shared or replicated.

Background jobs and queues

Move slow, non-interactive tasks out of the request path. The API validates a request, stores the job or publishes a message, and returns a job ID or accepted response. A worker processes it, records status and retries recoverable failures.

Four systems to practice

1. E-commerce backend

Core entities: users, products, inventory, carts, orders and payments.

Important concerns: reserve inventory safely, make payment requests idempotent, use transactions for related database updates, and handle payment-provider callbacks. Do not assume a payment and database transaction can be one atomic transaction across systems.

Possible components: API service, relational database, Redis cache, payment provider, queue and notification worker.

2. Chat application

Core entities: users, conversations, participants and messages.

Important concerns: WebSocket connections, message persistence, ordering within a conversation, reconnect behavior, delivery/read status and offline notifications.

Possible components: WebSocket gateway, message service, database, Redis for presence or coordination, and queue for notifications.

3. Notification service

Flow: producer creates a notification event, queue stores it, worker selects email/SMS/push provider, and delivery result is recorded.

Important concerns: retries, DLQ, provider timeouts, duplicate prevention, user preferences, templates and delivery status.

4. URL shortener

Flow: client submits long URL, service creates a unique short code, database stores mapping, and redirect endpoint looks it up.

Important concerns: code collision, unique constraint, expiration, abuse prevention, caching hot links and analytics. Use a fast lookup index on the short code.

Other terms to explain briefly

  • API Gateway: entry point for routing, authentication and cross-cutting API policies.
  • Service discovery: how services find the current network location of other services.
  • Replication: keeping copies of data on multiple database nodes.
  • Partitioning: splitting a large table or dataset into smaller pieces.
  • Sharding: distributing pieces of a dataset across multiple machines.
  • Observability: logs, metrics and traces used to understand system behavior.

8. Practical coding revision

Try each problem before looking at a solution. You should be able to explain edge cases and time/space complexity.

1. Promise.all (simplified)

Accept an array of promises or values. Resolve with results in input order when all succeed. Reject as soon as one rejects. Handle an empty array by resolving to an empty array.

function myPromiseAll(items) {
  return new Promise((resolve, reject) => {
    const values = [];
    let completed = 0;

    if (items.length === 0) return resolve([]);

    items.forEach((item, index) => {
      Promise.resolve(item).then(value => {
        values[index] = value;
        completed++;
        if (completed === items.length) resolve(values);
      }, reject);
    });
  });
}

This illustrates the core behavior. Native Promise.all also handles general iterables and specification details.

2. Debounce

Only run the function after calls have stopped for the chosen delay.

function debounce(fn, delay) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}

3. Retry with exponential backoff

async function retry(fn, attempts = 3, baseDelay = 200) {
  let lastError;

  for (let i = 0; i < attempts; i++) {
    try {
      return await fn();
    } catch (error) {
      lastError = error;
      if (i === attempts - 1) break;
      const delay = baseDelay * 2 ** i;
      await new Promise(resolve => setTimeout(resolve, delay));
    }
  }
  throw lastError;
}

Production retry code should add jitter, classify retryable errors and respect an overall timeout.

4. Simple in-memory rate limiter

function createRateLimiter({ limit, windowMs }) {
  const requests = new Map();

  return function rateLimit(req, res, next) {
    const key = req.ip;
    const now = Date.now();
    const entry = requests.get(key);

    if (!entry || now - entry.start >= windowMs) {
      requests.set(key, { start: now, count: 1 });
      return next();
    }

    if (entry.count >= limit) {
      return res.status(429).json({ error: "Too many requests" });
    }

    entry.count++;
    next();
  };
}

This is only suitable as a learning example or for a single process. The map grows unless expired entries are cleaned up, and multiple instances need a shared atomic store such as Redis.

5. Concurrent task queue

Build a function that accepts tasks and a concurrency limit. At most N tasks should run at once. Preserve result order, and decide whether one failure should stop the queue or be returned as an individual result.

6. Custom EventEmitter

Implement on(event, callback), off(event, callback), emit(event, ...args) and optionally once(). Think about duplicate listeners, removing listeners during emission and memory cleanup.

7. Express authentication middleware

function requireAuth(req, res, next) {
  const header = req.headers.authorization;
  const token = header?.startsWith("Bearer ")
    ? header.slice(7)
    : null;

  if (!token) {
    return res.status(401).json({ error: "Unauthenticated" });
  }

  try {
    req.user = verifyToken(token); // use a trusted JWT library
    next();
  } catch {
    res.status(401).json({ error: "Invalid or expired token" });
  }
}

Do not write your own cryptographic JWT verification. Validate signature, allowed algorithm, issuer, audience and expiry using a maintained library and trusted configuration.

8. SQL: second-highest distinct salary

SELECT MAX(salary) AS second_highest_salary
FROM employees
WHERE salary < (
  SELECT MAX(salary) FROM employees
);

This returns NULL if there is no second distinct salary. Be ready to solve variants using DENSE_RANK().

9. Quick-fire interview questions

Practice answering each in 30–60 seconds. Expand to reveal a short answer.

How does Node.js handle many requests with one main thread?

It uses non-blocking I/O. The main thread starts work and does not wait for most I/O operations to finish. When results are ready, callbacks are scheduled for JavaScript to process. CPU-heavy JavaScript can still block the event loop.

Why should we use streams for large files?

Streams process chunks of data rather than loading the entire file into memory. They reduce memory pressure and can apply backpressure when the destination is slower than the source.

Why is a database index not always good?

Indexes consume storage and make writes more expensive because the database must maintain them. An index helps only when its structure matches useful query patterns.

What is the difference between 401 and 403?

401 means the request lacks valid authentication. 403 means the server understood the identity or request but refuses access due to permissions or policy.

How do you prevent duplicate payment processing?

Use an idempotency key, persist its status and result, enforce uniqueness atomically, and make provider callbacks safe to process more than once.

What happens if Redis goes down?

It depends on its role. If it is only a cache, fall back to the database carefully and protect it from a traffic spike. If it stores sessions, locks or queue data, the impact is greater and needs a specific recovery strategy.

When would you choose a queue instead of an HTTP call?

Use a queue when work can happen asynchronously, should be retried, or needs buffering during traffic spikes. Use a direct HTTP call when the caller needs an immediate response and synchronous coupling is acceptable.

How would you debug a slow API?

Measure request latency, inspect logs and traces, identify time spent in application code versus dependencies, inspect database query plans, check connection pools and external API latency, then profile CPU or memory if needed.

What is the difference between horizontal and vertical scaling?

Vertical scaling increases resources on one machine. Horizontal scaling adds more instances. Horizontal scaling can improve capacity and resilience but requires handling shared state, load balancing and coordination.

What is eventual consistency?

Different copies or services may temporarily show different data after an update, but they are expected to converge over time. Applications must account for that delay.
